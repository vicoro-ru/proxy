## Пояснения по конфигурации HAProxy
### Режим работы
Ниже приведён разбор ключевых параметров `haproxy.cfg`, используемого в этом проекте.
В текущем режиме он работает на уровне TCP соединения не залезая внутрь контента что и хорошо
### Блок `global`
Где мы указали что выводим их в stdout, в формате raw (надо уточнить про формат), (local0 тоже)
Macconn это соедениения, так как режим работы TCP то соединения от одного пользователя может быть множество. Если открыть любую вкладку сайта то каждый забранные файлик это и есть соеденинение, у одного youtube их сотни
```sh
global
    log stdout format raw local0
    maxconn 8192
```
### Блок defaults
Где:
log global — наследует параметры логирования из блока global.
option httplog — формат логов, ожидает http (это: URL, статус, заголовок), но так как мы на уровне tcp модели osi то такой формат не нужен
option tcplog - tcp логи
option dontlognull — отключает логирование пустых соединений которые открылись и тутже закрылись, по этому на отладке не нужны, но в целом в рабочем режиме лучше поставить
option  log-health-checks - выводить в логи проверки здоровья выходных шлюзов (почему отключаем не понятно)
timeout connect 30s — максимальное время попытки подключения к backend (узлу tor+privoxy).
timeout client 5m — время ожидания активности от клиента (squid), youtube и прочие чаты могут минуты ничего не делать
timeout server 50s — время ожидания активности от backend'а (privoxy), тоже долго могут молчать
```sh
defaults
    log     global
    # option  log-health-checks
    option tcplog
    timeout connect 30s
    timeout client  5m
    timeout server  5m
```


### Блок frontend
```sh
frontend privoxy_in
    bind *:8118
    default_backend tor_privoxy_pool

    frontend privoxy_in — объявляем точку входа для клиентов.

    bind *:8118 — HAProxy слушает порт 8118 на всех интерфейсах контейнера.

    default_backend tor_privoxy_pool — весь трафик уходит в backend-пул, где крутятся tor+privoxy.
```
### Блок backend
```sh
backend tor_privoxy_pool
    balance roundrobin
    option httpchk GET /
    server-template proxy 10 proxy-node:8118 check resolvers docker init-addr none
    resolvers docker
        parse-resolv-conf
        hold valid 10s
```
    balance roundrobin — распределение запросов равномерно между всеми доступными узлами.

    option httpchk GET / — активная проверка доступности backend'а простым HTTP-запросом.

    server-template proxy 10 proxy-node:8118 ...

        proxy — базовое имя серверов (HAProxy сам создаст proxy1, proxy2 и т.д.).

        10 — максимальное количество ожидаемых контейнеров (можно увеличить при росте пула).

        proxy-node:8118 — имя сервиса в Docker (Docker DNS отдаст IP всех контейнеров этого сервиса).

        check — включает мониторинг доступности.

        resolvers docker — используем кастомный резолвер для динамического поиска IP.

        init-addr none — говорит не пытаться резолвить имя сразу при запуске (ждём появления контейнеров).

    resolvers docker

        parse-resolv-conf — использует настройки DNS внутри контейнера (обычно это Docker DNS).

        hold valid 10s — кэшировать DNS-записи 10 секунд.

### Итог
Эта конфигурация позволяет:
Балансировать между любым числом контейнеров tor+privoxy без ручного указания их IP.
Автоматически добавлять новые контейнеры, если их поднять через docker compose scale.
Исключать «падающие» узлы из пула без ручного вмешательства.

Разбор основного блока
haproxy

backend tor_privoxy_pool
    # 1. Режим работы
    mode tcp 
    # Комментарий: Мы работаем на уровне потока данных (L4). 
    # Это быстрее, чем 'mode http', так как HAProxy не вскрывает пакеты, 
    # а просто перебрасывает их. Для Tor это лучший выбор.

    # 2. Метод балансировки
    balance source
    # Комментарий: Это "липкая" балансировка. HAProxy берет ваш IP, делает из него хэш 
    # и закрепляет за вами один из 50 прокси. 
    # Зачем: Чтобы YouTube не выдал 403 Forbidden. Google привязывает ссылку на видео 
    # к IP прокси. Если первый кусок видео вы скачали через "Proxy 1" (Франция), 
    # а второй через "Proxy 2" (Швеция) — видео прервется. 'source' это предотвращает.

    # 3. Проверка работоспособности (Health Check)
    option httpchk GET http://check.torproject.org/
    http-check send hdr Host check.torproject.org
    # Комментарий: HAProxy не просто верит, что контейнер запущен, он реально 
    # заходит через этот прокси на сайт Tor Project. 
    # Если сайт ответил (код 200/301) — значит, Tor внутри контейнера построил цепочку.

Используйте код с осторожностью.
Разбор строки генерации серверов (Критический момент)
haproxy

server-template proxy 50 tasks.tor:8118 check inter 15s fall 5 rise 2

Используйте код с осторожностью.

    server-template proxy 50: Автоматически создает 50 записей серверов (proxy1, proxy2... proxy50). Очень удобно для Docker Swarm, не надо писать 50 строк вручную.
    tasks.tor:8118: Специфический адрес Docker Swarm. Он вернет IP-адреса всех запущенных реплик сервиса tor.
    check: Включает проверку (тот самый httpchk выше).
    inter 15s (Интервал): Как часто мучить Tor проверкой. В старом конфиге стояло по умолчанию (2 сек). В новом — 15 секунд.
        Зачем: Слишком частые проверки «забивают» канал Tor и могут привести к тому, что сайт проверки забанит ваш выходной узел.
    fall 5 (Порог падения): Сколько раз проверка должна провалиться подряд, чтобы HAProxy пометил прокси как «мертвый».
        Зачем: Tor в 2026 году нестабилен. Провалы на 2-5 секунд — норма. Ставя fall 5, мы говорим: «Если прокси тормозит — это нормально, не выключай его сразу. Выключай, только если он реально сдох и не отвечает больше минуты (15с * 5)».
    rise 2 (Порог восстановления): Сколько раз прокси должен пройти проверку, чтобы вернуться в строй. 2 раза — оптимально, чтобы убедиться, что он не «моргает».

Обработка ошибок (Механизм выживания)
haproxy

    option redispatch
    retries 3

Используйте код с осторожностью.

    retries 3: Если HAProxy попытался отправить ваш запрос на выбранный прокси, но тот внезапно «отвалился» (Connection Refused), он попробует еще 2 раза.
    option redispatch: Это «спасательный круг». Если после всех попыток (retries) ваш закрепленный прокси (balance source) так и не ответил, HAProxy плюнет на правила, «отлепит» вас от этого прокси и перекинет на другой живой.
        Для YouTube: Это может вызвать кратковременный затык или 403, но это лучше, чем бесконечное ожидание на мертвом узле.


option tcp-smart-connect

HAProxy сначала устанавливает TCP-соединение с backend’ом
и только если оно успешно — принимает соединение от клиента.

Зачем:

не держать «висящие» клиентские TCP-сессии

быстрее отдавать отказ, если backend не доступен

экономить сокеты и ресурсы HAProxy

Что это НЕ:

❌ не анализирует HTTP / HTTPS

❌ не лечит блокировки

❌ не влияет на L7

❌ не чинит Tor или интернет

Уровень:

✔ L4 (TCP)

работает до любого HTTP / TLS / CONNECT

Типичная польза:

медленные или нестабильные backend’ы (Tor, VPN, прокси)

ситуации, где TCP может зависнуть на connect

Ключевая мысль:

Лучше не принять клиента вообще,
чем принять и держать его в вечном ожидании.
